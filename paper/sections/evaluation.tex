\subsection{Methodology}
\label{sec:eval:method}

\paragraph{Hardware.}
All benchmarks were conducted on a workstation equipped with an NVIDIA RTX A6000
GPU (48~GB GDDR6 VRAM, Ampere architecture, 309~GB/s memory bandwidth).
The host runs Ubuntu 22.04 with CUDA 12.2 and driver 535.

\paragraph{Software stack.}
The VisionServe Go HTTP server was built with Go~1.22 and linked against
ONNX Runtime~1.17 \cite{onnxruntime} with the CUDA Execution Provider enabled.
Model artefacts are exported ONNX files; no TensorRT engine cache was used so
that results are reproducible across machines without a TensorRT installation.
The ONNX format and runtime are described in \cite{onnx2019}.

\paragraph{Benchmark protocols.}
We use \emph{two} distinct protocols, and are careful throughout not to conflate
them.
\emph{(a) Per-model single-stream latency} (Table~\ref{tab:benchmark}): for each
model, five warm-up requests were issued and discarded to ensure the ONNX session
was fully initialised and any JIT optimisation passes had completed; twenty timed
requests were then issued \emph{sequentially} from a single-threaded HTTP client over
the loopback interface (\texttt{localhost:11435}), and all p50/p95 figures in
Table~\ref{tab:benchmark} are reported over these 20 requests.  The RPS column of
Table~\ref{tab:benchmark} is therefore a \emph{single-stream} rate (the reciprocal of
mean end-to-end latency at concurrency~1), and is \emph{not} a saturated-throughput
number.
\emph{(b) Concurrency-sweep throughput} (Tables~\ref{tab:crossover} and
\ref{tab:tensorin}): the crossover and peak-goodput results were obtained with the
closed-loop load-generation harness (\texttt{eval/loadgen/sweep\_openloop.py}), which
holds a fixed number of in-flight requests $C$ and records completed-request rate and
HdrHistogram percentiles over a 20\,s window per concurrency level.  Unless stated
otherwise, throughput results use this harness with the same JPEG input
(\texttt{sample.jpg}, $810\times1080$) and the same ONNX file for every system.

\paragraph{Metrics.}
\begin{itemize}
  \item \textbf{p50 / p95} — 50th and 95th percentile of \emph{end-to-end HTTP
    latency} (wall-clock time from client send to response received), in milliseconds.
    This includes HTTP serialisation, Go image decoding and preprocessing, ONNX
    inference, postprocessing, and JSON serialisation.
  \item \textbf{srv\_p50} — 50th percentile of \emph{server-side inference latency},
    defined as the time spent exclusively inside ONNX session \texttt{Run} calls.
    This isolates pure tensor-computation cost from Go-layer overhead.
  \item \textbf{RPS} — \emph{single-stream} rate in requests per second at batch
    size~1, derived from the mean end-to-end latency under protocol~(a).  This is the
    throughput of one sequential client, \emph{not} the saturated throughput; the
    latter is measured separately by the concurrency sweep
    (Section~\ref{sec:eval:python}).
  \item \textbf{VRAM (MB)} — peak GPU memory as reported by \texttt{nvidia-smi
    --query-compute-apps} at inference time, after the session is warm.
  \item \textbf{ONNX (MB)} — size of the ONNX model file(s) on disk.
  \item \textbf{Cold-start (s)} — elapsed time from process start (before any request)
    to the completion of the first successful inference, measuring model load from disk,
    ONNX session initialisation, and provider graph optimisation.
\end{itemize}

\paragraph{Comparability of server-side timers.}
One subtlety governs every VisionServe-vs-baseline comparison below.  VisionServe's
internal \texttt{duration\_ms} counter spans preprocess~+~ORT~Run~+~postprocess, whereas
the FastAPI+ONNX-Runtime baseline's server-side timer covers ORT~Run only (it excludes
its own Pillow decode and tensor marshalling).  The two \texttt{duration\_ms} values are
therefore \emph{not} directly comparable, and we never compare them as raw server-side
numbers.  All head-to-head latency and throughput figures use instead the
\emph{client-measured end-to-end} time (HdrHistogram, measured by the load generator
outside both servers), which charges every system for its full decode$\to$infer$\to$
respond pipeline on the identical wire input — the only apples-to-apples metric.

\paragraph{Classification and embedding.}
The three lightest models — CLIP \cite{radford2021clip}, MobileNetV3
\cite{howard2019mobilenetv3}, and EfficientNet-B0 \cite{tan2019efficientnet} — achieve
p50 latencies of 33--40~ms and sustain 23--28~RPS.  Their \texttt{srv\_p50} values of
12--21~ms reveal that ONNX inference itself is very fast; the remaining 15--20~ms is
dominated by Go-side JPEG decoding, tensor allocation, and JSON serialisation.  These
models are well-suited to high-throughput pipelines where embedding or top-$k$
classification is a preprocessing step.

\paragraph{Detection.}
The four detection models (SCRFD \cite{guo2021scrfd}, PaddleOCR \cite{du2020ppocr},
RF-DETR-Nano, and RF-DETR) cluster between 45 and 78~ms.  SCRFD achieves the lowest
latency at 45~ms p50 while consuming only 420~MB VRAM, making it the most efficient
choice for face-detection workloads.  RF-DETR-Nano and RF-DETR
are NMS-free transformer detectors; their slightly higher latency (57~ms and 78~ms)
reflects the cost of the attention mechanism, but they offer general-purpose
object detection across the full COCO vocabulary.  PaddleOCR's 54~ms p50 includes
text-detection preprocessing suited to document images.

\paragraph{Segmentation.}
The three segmentation models require 161--242~ms p50 owing to their encoder--decoder
architectures.  Notably, \texttt{srv\_p50} is very close to the total p50 for all three
(138~ms vs.\ 161~ms for MobileSAM \cite{zhang2023mobilesam}; 158~ms vs.\ 181~ms for
EfficientSAM \cite{xiong2023efficientsam}; 222~ms vs.\ 242~ms for SAM2
\cite{ravi2024sam2}), confirming that inference dominates and Go overhead is negligible
at this scale.  SAM2's p95 of 544~ms indicates higher variance, likely from attention
computation over longer context windows.

\paragraph{Open-vocabulary detection.}
GroundingDINO \cite{liu2023groundingdino} is the heaviest single model at 570~ms p50,
consuming 4.4~GB VRAM and a 693~MB ONNX file.  This cost is the price of its unique
capability: detecting arbitrary object categories described in natural language at
request time, without any fixed class vocabulary.  Its \texttt{srv\_p50} of 548~ms
confirms that the dual-encoder (Swin-T image + BERT text) computation accounts for
nearly the entire latency.  At 1.7~RPS it is unsuitable for high-frame-rate video,
but practical for query-driven image analysis.

\paragraph{Tensor input: isolating the decode deficit.}
The end-to-end results above charge VisionServe for server-side image decode and
preprocessing on every request.  To isolate the runtime from that cost, we added a
\texttt{POST /api/infer\_tensor} endpoint that accepts a raw NCHW \texttt{float32}
tensor and skips JPEG/PNG decode and preprocessing entirely, then compared against
NVIDIA Triton serving the same MobileNetV3-Small ONNX.  Table~\ref{tab:tensorin}
reports closed-loop throughput and latency on the A6000.  With a pre-decoded tensor,
VisionServe's single-request latency drops to a p50 of 8.1~ms (min 3.4~ms) at 118~rps,
versus 12.7~rps / 57~ms for the JPEG-in path, and its concurrency-64 peak of 563~rps
essentially matches a \emph{default-configuration} Triton (HTTP front end, a single
model instance, no dynamic batching), which peaks at $\sim$549~rps with a comparable
2.9~ms single-request floor.  In the no-decode regime the two runtimes are therefore
within measurement noise (peak 563 vs.\ 549~rps; min 3.4 vs.\ 2.9~ms), indicating that
VisionServe's earlier low-load deficit was attributable to server-side image decode
rather than the ONNX serving path itself.  We stress that the Triton figure is its
out-of-the-box default; enabling dynamic batching or multiple instances would raise
Triton's ceiling, and we do not claim parity against a tuned Triton deployment.

\paragraph{The decode-parallelization twist.}
Counter-intuitively, VisionServe's \emph{JPEG-in} peak goodput (695~rps,
Table~\ref{tab:crossover}) exceeds its \emph{tensor-in} peak (563~rps).  Pure-Go JPEG decode is CPU-heavy but
embarrassingly parallel across goroutines and cores, so under concurrency the decode
work overlaps with GPU inference and the server saturates more work overall.  The
tensor-in path removes that parallel CPU work and becomes GPU-mutex- and HTTP-bound,
exactly like Triton---which is precisely why its ceiling converges with Triton's rather
than exceeding it.  On the client side, the choice of wire format dominates round-trip
cost from an \texttt{np.ndarray}: a raw tensor submission measures $\sim$8~ms end to end,
versus $\sim$64~ms for a JPEG round-trip and $\sim$136~ms for PNG.

\subsection{Cold-Start Analysis}
\label{sec:eval:coldstart}

Cold-start time measures the elapsed duration from process initialisation to the
completion of the first successful inference.  It includes reading the ONNX file from
disk, allocating and initialising the ONNX Runtime session, running provider-specific
graph optimisations (e.g.\ CUDA kernel compilation), and warming up the GPU memory
allocator.

Figure~\ref{fig:coldstart} shows cold-start times for all 12 benchmarked models.
The range spans 2.1~s (MobileNetV3) to 9.2~s (GroundingDINO), with most models
falling between 3 and 6 seconds.  Cold-start time correlates broadly with model file
size: the three models above 5~s (CLIP at 5.8~s, EfficientSAM at 5.8~s, and
GroundingDINO at 9.2~s) are also among the largest ONNX files (335~MB, 39~MB, and
693~MB respectively).  GroundingDINO's 9.2~s startup is further prolonged by
BERT tokenizer initialisation and the dual-session graph.

VisionServe's \texttt{lifecycle.Manager} keeps every session alive in GPU memory after
the first load.  Subsequent requests pay only the inference cost; cold-start is
therefore a one-time penalty per process lifetime, not per request.

\subsection{Comparison with a Python Baseline}
\label{sec:eval:python}

Mainstream CV model-serving stacks are built around Python runtimes — most commonly
Flask or FastAPI fronting a PyTorch \texttt{model.forward()} call, or higher-level
frameworks such as TorchServe \cite{pytorch2023torchserve} and BentoML.  To make a
fair, like-for-like comparison we measured a FastAPI+ONNX-Runtime baseline directly:
the \emph{same} MobileNetV3-Small and EfficientNet-B0 ONNX files, the same CUDA
Execution Provider, the same A6000 host, and the same load generator and JPEG input as
VisionServe.  The baseline is the deployed default — a single \texttt{uvicorn} worker
with one ONNX Runtime session (\texttt{SESSION\_POOL=1}) — so that any concurrency
result is scoped to the GIL-bound CPython configuration most teams actually ship, not a
hand-tuned multi-process deployment.  VisionServe ran on GPU\,2 and the baseline on
GPU\,3 of the same node; all rows reported below recorded \texttt{errors}=0.

\paragraph{The crossover.}
Table~\ref{tab:crossover} reports the closed-loop concurrency sweep for MobileNetV3-Small.
The two systems exhibit a clean \emph{crossover}.  At low concurrency the Python baseline
is faster per request — at $C{=}1$ its end-to-end p50 is 16.1\,ms versus VisionServe's
57.2\,ms — and it correspondingly delivers higher single-client throughput (66.0 vs.\
12.7\,rps).  Computing $\Delta(C)=\text{rps}_{\text{VS}}-\text{rps}_{\text{FastAPI}}$ and
locating the zero-crossing places the crossover at $C^\star\!\approx\!4$ for both
MobileNetV3-Small ($\Delta$ flips from $-1.8$ at $C{=}4$ to $+114.9$ at $C{=}8$) and
EfficientNet-B0 ($C^\star\!\approx\!4.4$).  Above the crossover VisionServe pulls away
sharply: at $C{=}64$ it sustains 694.6\,rps against the baseline's 84.6\,rps — a
$\sim$8$\times$ peak-goodput advantage on identical ONNX.  EfficientNet-B0 follows the
same shape, with VisionServe reaching 510\,rps against the baseline's 76.6\,rps at $C{=}64$.
The baseline never scales: its throughput is essentially flat ($\sim$66$\to$87\,rps,
peaking at $C{=}8$) and its latency degrades catastrophically with load (p50 climbs from
16\,ms at $C{=}1$ to 755\,ms at $C{=}64$), because a single \texttt{uvicorn} worker with
one ONNX session is GIL- and single-session-bound and cannot use additional in-flight
requests.  Because the \emph{same} 64-way client drove VisionServe to 695\,rps, the
baseline's $\sim$85\,rps plateau is a real server-side limit, not a client artefact;
VisionServe's own ceiling may be higher still under a native (non-Python) load generator,
so these figures are conservative for VisionServe.

\paragraph{Why VisionServe loses at low load (and why it is not the GPU).}
We state the low-load regression plainly rather than hiding it: at $C{=}1$ VisionServe is
$\sim$3.6$\times$ slower per request than the FastAPI baseline (p50 57.2 vs.\ 16.1\,ms;
min 25.9 vs.\ 10.9\,ms).  A latency decomposition (Table~\ref{tab:benchmark}'s
\texttt{srv\_p50}, corroborated by a standalone Go benchmark of the decode/preprocess
stages) shows this cost is \emph{not} the GPU.  On this host the ONNX Runtime
\texttt{Run} call is under 1\,ms, ImageNet resize+normalise is $\sim$3.6\,ms, and the
dominant term is pure-Go JPEG decode (\texttt{image/jpeg}) at $\sim$19.2\,ms — which
alone accounts for VisionServe's $\sim$25.9\,ms $C{=}1$ \emph{min} latency.  The baseline
is faster per request only because Pillow decodes via libjpeg-turbo (SIMD), a few
milliseconds.  Crucially, the same property that costs VisionServe at $C{=}1$ is what wins
under load: pure-Go decode is CPU-heavy but embarrassingly parallel across goroutines and
the host's 48 cores, so as $C$ rises the decode work overlaps inference and aggregate
throughput climbs, whereas the GIL-bound single-worker baseline cannot parallelise.  This
is the CV-specific instance of the ``beyond inference'' observation that non-model overhead
governs throughput for small nets on fast GPUs.  The decode tax is recoverable: a
build-tagged libjpeg-turbo decode would cut the $\sim$19\,ms toward $\sim$4\,ms, but it
breaks single-static-binary portability, so we keep pure-Go and report the gap rather than
silently take the cgo win.

\paragraph{Concurrency model: where the parallelism actually comes from.}
The scaling above is enabled by Go goroutines and OS threads with no process-level
interpreter lock, but we are careful not to overstate the runtime: a single ONNX Runtime
session in VisionServe is itself mutex-serialised (\texttt{engine.Session.Run} holds a
per-session lock), so concurrent requests routed to the same session run one at a time,
just as a GIL would serialise them.  At $C{=}64$ the observed scaling therefore comes
overwhelmingly from parallel \emph{decode and preprocess} across cores overlapping a
sub-millisecond, mutex-serialised GPU \texttt{Run}, not from parallel inference.  Genuine
intra-process inference parallelism is available through the per-role \emph{session pool}
(\texttt{engine.SessionPool}): when a role is configured with a pool size $>1$, the
\texttt{lifecycle.Manager} holds several identical sessions and dispatches each request to
the first free one, so up to $N$ inferences proceed without a shared lock.  The pool size
is configurable per role (via the \texttt{VS\_POOL\_OVERRIDE} load-time setting) and
defaults to~1; the image-input sweeps above use that default, so the 8$\times$ JPEG-in result
is achieved \emph{without} multi-session inference.  This is appropriate: in the image-input
regime the bottleneck is the (already core-parallel) Go decode/preprocess, not the
mutex-serialised \texttt{Run}, so pooling cannot help there.  Pooling matters precisely in the
\emph{tensor-input} regime, where decode is absent and the per-session \texttt{Run} mutex
\emph{is} the ceiling.  Table~\ref{tab:pool} confirms this: sweeping the pool size on the
tensor-in path lifts peak goodput from 718\,rps at pool~1 to 1438\,rps at pool~4 --- a
2.0$\times$ gain from removing the mutex serialisation --- with diminishing returns by pool~8
(1653\,rps) as GPU compute itself saturates.  This both validates the mutex analysis and shows
the serialisation is configurable away exactly when inference, not decode, is the limit.

\paragraph{Sustainable load under an SLO.}
Closed-loop peak goodput rewards a system for absorbing a backlog; an open-loop,
constant-offered-rate view under a latency SLO is the stricter test.
Table~\ref{tab:openloop} sweeps the offered rate on MobileNetV3-Small under HdrHistogram
timing.  Under a p50~$<$~50\,ms target, the FastAPI baseline holds $\sim$50\,rps
(p50~$<$~20\,ms) and then \emph{collapses} abruptly at an offered 100\,rps, where its p50
jumps to $\sim$6.3\,s and goodput falls to $\sim$62\,rps; it refuses connections beyond an
offered $\sim$600\,rps.  VisionServe instead holds $\sim$200\,rps at p50~$\sim$31\,ms with
zero errors, degrading only past 400\,rps (where its p50 of 805\,ms breaches the SLO).  So
under the same SLO VisionServe sustains roughly 4$\times$ the baseline's load with no errors
where the baseline begins dropping connections.

We are deliberately self-critical about the \emph{tail}, however: VisionServe's open-loop
p99.9 is already heavy inside this nominally-healthy regime (658\,ms at an offered 100\,rps,
909\,ms at 200\,rps), even while its p50 stays at $\sim$30\,ms and \texttt{errors}=0.  We do
not believe this tail reflects a server limit.  Most likely it is an artefact of the
pure-Python load generator's own scheduling jitter, coordinated omission, and garbage
collection rather than the server: the \emph{same} VisionServe build reaches 695\,rps in the
closed-loop run (Table~\ref{tab:crossover}) with a p99 of only $\sim$108\,ms at $C{=}64$, and
the open-loop goodput plateaus at $\sim$390\,rps — exactly coinciding with the pure-Python
client's measured throughput cap.  To settle this we re-measured the open-loop tail with
\texttt{vegeta}, a native Go coordinated-omission-correct generator that is not subject to the
Python client's cap.  The native measurement confirms the diagnosis: on the image-input path
VisionServe sustains an offered 400\,rps at 100\,\% success with a p99.9 of only \textbf{71\,ms}
(p50~39\,ms) --- against the pure-Python client's 909\,ms p99.9 at a \emph{lower} 200\,rps ---
and the server's true knee appears near 600\,rps, where p99.9 rises to $\sim$1.8\,s as the
decode pipeline saturates.  The earlier heavy p99.9 was therefore a client artefact, exactly as
suspected: under a native generator VisionServe's image-input tail is in fact well-behaved up to
its real ($\sim$600\,rps) saturation point, and the open-loop ceiling reported by the Python
client was understated.  The offered-$\geq$800\,rps baseline ``goodput'' rows are 100\,\% failed
(connection-refused) requests and are excluded as invalid.

\paragraph{Cold-start, lifecycle, and footprint.}
Python-based servers also incur a cold-start penalty from interpreter startup,
\texttt{import torch}, and CUDA context initialisation, typically several seconds on top of
model load; the VisionServe binary starts the ORT library directly via a CGO binding
\cite{onnxruntime}, with no interpreter to initialise.  Serving four models from one
process, VisionServe occupied 917\,MB RSS and 920\,MB VRAM at idle, versus four Python
processes at 1632\,MB RSS and 1384\,MB VRAM — a saving of 715\,MB RSS ($-44\%$) and 464\,MB
VRAM ($-34\%$).  For heavyweight, inference-dominated models such as GroundingDINO
(570\,ms p50, Table~\ref{tab:benchmark}) the relative Go-vs-Python overhead shrinks; the Go
approach is most beneficial in the lightweight and medium-latency regime (33--78\,ms models)
where decode and dispatch are a significant fraction of total latency.
